# Moonbow 思想溯源与架构设计

本文记录 Moonbow 范式的完整推导过程：五次实证迭代如何一步步逼近核心洞察，以及由此推出的项目架构。

---

## 1. 起点：一个来自真实会话的观察

在整理个人 Agent 历史会话、归类错误模式时，注意到一个稳定复现的现象：

**LLM 执行长程任务时，存在两个同步的崩塌过程。**

1. **依从度崩塌**：对任务开始时规划好的 plan，执行依从度随轮次逐渐下降，直至完全失效；
2. **全局视角崩塌**：对任务整体的把握逐渐丢失，最终钻进某个细节的牛角尖。

两者的终点一致：需要人介入，重新对齐、引导方向。而人在这种工作中的实际角色，与其说是协同创作者，不如说更接近一个 **DAG 式的调度执行者**——维护目标结构、检查完成状态、决定下一步派发什么。

### 已有方案的局限

`/GOAL` 类模式能解决一部分问题，但只能锁定 GOAL 中被显式定义的行为；它无法维持长程任务的全局视角，也无法阻止子目标的静默丢失。

### 诊断

问题的瓶颈不是 LLM 智力不足，而是 **LLM 不善于执行"程序化的流程"**。即使后续模型迭代专门对齐了这类能力，表现依然不稳定——尤其是经过上下文压缩之后。

由此得出第一原则：

> **能被固定化、程序化的流程，应该由程序约束和门禁来确保执行，而不是在 prompt 里写自然语言程序赌概率。**

## 2. 五次实证迭代

### 迭代一：程序化插件（有效，但太薄）

- [pi-todone](https://github.com/Nuctori/pi-todone) —— 树形 todo 义务与完成证明
- [pi-dag-core](https://github.com/Nuctori/pi-dag-core) —— DAG 任务编排

以程序化插件的形式注入生命周期，配合 skill 作为说明书。**结论**：程序化约束确实有效，但依旧无法扭转目标漂移和用户意图丢失。

**推断**：LLM 在长程工作中关注点过多，"关注点丢失"是必然发生的，规则插件覆盖不了语义层的漂移。

### 迭代二：后台结对者（有效，但太贵）

- [pi-pair](https://github.com/Nuctori/pi-pair) —— 维护一个后台 subagent，以结对编程的思路持续跟踪用户意图的履行情况和产物质量。

**结论**：交付精度显著提高，单个 Agent 的全局目标丢失问题极大缓解。但时间成本和 token 成本同步大幅上升——等于给每个主 Agent 配了一个全职的大模型监工。

### 关键观察

结对者需要执行的工作有三个特征：**十分简单、边界定义明确、高度程序化**。它不需要创造力，不需要领域知识，不需要长程记忆——却占用着一个昂贵的大参数模型和大量时间。

### 迭代三：训练专门小模型（失败，但发现关键点）

尝试形式化定义任务边界，专门训练一个小模型负责这部分工作——把语言模型视作**针对自然语言的模式匹配算子**，高吞吐、低延迟地解决它。

受限于算力（单张 A770）和语料（只有自己的真实工作会话），训练并不成功。但失败中浮现出一个关键点：

> **只要把一个认知任务拆成"定量"和"定性"两半，组合两类模型——确定性程序负责定量裁决，语言模型负责定性匹配——在不需要任何训练的前提下，就能以工程可接受的准确度获得被定义的能力。**

定性模型不需要理解任务全貌，只需要回答一个窄问题（"这两段话说的是同一个对象吗""这个语气是断言还是含糊"）；剩下的一切交给程序。本仓库的 progress-guard 就是这个发现的第一次完整落地。

### 迭代四：三层结构模型

把一个工作着的智能体拆解为三个组成部分：

| 层 | 内容 | 特点 |
|---|---|---|
| L1 | 冻结的语言模型权重 | 真正内化的能力；更新成本巨大 |
| L2 | 冻结的 harness（skill、MCP、AGENTS.md） | 更新成本低；但上下文不是内化能力，只是**关注点的引导**——上限低且容易过期（SkillOpt 类方法的局限） |
| L3 | 通过实时推理得到的上下文知识 | 每次从零组装；所有未被下层覆盖的负担都压在这里 |

被冻结的部分越多、越靠上层，实时推理承担的工作和负担就越少。但 L1 更新太贵，L2 便宜却"定义了但没内化"。

### 结论：两个冻结层之间的甜点区

L1 与 L2 之间存在一个甜点区，Moonbow 就落在这里：

> **将 Agent 的工作视为自然语言流的持续产出。通过组合拥有自然语言理解能力的小模型，低成本、高吞吐地解决大部分边界明确定义的问题。**

它同时解决两个死结：

- skill 的"**定义了但没内化**"（管线由 harness 强制执行，不依赖模型自觉）；
- 微调权重的"**内化了但成本高**"（窄带小模型 + 确定性状态机，零训练或极低训练成本）。

并且这条路是可递归的：**挖掘问题 → 定义问题边界 → 拓展管线**。每消化一类系统性失败，管线就多一个节点。这意味着智能体能力可以在工程层面持续自我扩展——在一定程度上，这是通往 RSI 的一条可控路径。

## 3. 架构设计

### 3.1 总体分层

```
┌─────────────────────────────────────────────────────────────┐
│  宿主适配层  harness adapters                                 │
│  Pi 扩展 / HTTP 微服务 / CLI —— 把生命周期事件翻译成流事件      │
├─────────────────────────────────────────────────────────────┤
│  管线运行时  pipeline runtime                                 │
│  流抽象 · 节点编排 · 状态机门禁 · 审计日志                      │
├─────────────────────────────────────────────────────────────┤
│  节点库  nodes                                                │
│  定性节点（微模型） + 定量节点（规则/阈值/协议解析）             │
├─────────────────────────────────────────────────────────────┤
│  领域插件  plugins                                            │
│  progress-guard（当前）· 意图对齐 · 目标回归（规划中）          │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 核心抽象

**Stream（流）**——Agent 产出的自然语言流是一等公民。宿主适配层把 harness 生命周期事件（`context`、`turn_end`、`message_end`）翻译成流事件；管线订阅流，而不是被动等待调用。

**Node（节点）**——管线的最小单元，分两类：

- **定量节点**：协议解析、阈值比较、规则拦截、外部工具结果核对。确定性、可单测、成本为零；
- **定性节点**：微模型推理（模态分类头、二值捕获头、相似度编码器）。只回答一个定义良好的窄问题，毫秒级。

**Gate（门禁）**——节点输出不直接决定行为。所有节点输出汇入确定性状态机，由状态机聚合成裁决（`BLOCK` / `CLARIFY` / `CLOSE`）并维护轮次记忆（如非对称争议放行）。这是可审计性的来源：每一次裁决都可复现。

### 3.3 设计原则

1. **判决尽量下沉到定量节点**，定性节点只处理灰色带——定量部分零成本、可证伪，定性部分小而准；
2. **成本不对称硬约束**：守卫侧的总成本（延迟、内存、token）必须比主模型低 2~3 个数量级，否则就退化了迭代二的 pi-pair 困局；
3. **节点独立可替换**：每个节点解决一个定义良好的问题，输入输出有明确契约，坏一个换一个，不动管线；
4. **无侵入**：主模型不感知管线存在。不需要它配合、遵守格式以外的任何约定，也不占用它的工具空间和上下文预算；
5. **可递归扩展**：新问题的接入流程固定为——观察 Agent 系统性失败 → 形式化定义边界 → 拆成定量/定性两半 → 选现成节点或新增窄带微模型 → 冻结为管线段。

### 3.4 目标包结构

```
moonbow/
├── src/moonbow/
│   ├── core/                # 管线运行时
│   │   ├── stream.py        #   流事件抽象（来源：宿主生命周期）
│   │   ├── node.py          #   节点协议（定性/定量统一接口）
│   │   ├── pipeline.py      #   声明式编排（配置即管线）
│   │   └── gate.py          #   状态机门禁与裁决原语
│   ├── nodes/               # 内置节点库
│   │   ├── protocol.py      #   清单协议解析（定量）
│   │   ├── modality.py      #   语气模态分类（定性）
│   │   ├── similarity.py    #   客体对齐相似度（定性）
│   │   └── capture.py       #   完成度捕获（定性）
│   ├── plugins/
│   │   └── guard/           #   progress-guard：收尾闭合门禁（已落地：src/moonbow/guard）
│   ├── adapters/
│   │   ├── pi.ts            #   Pi Agent 扩展
│   │   ├── server.py        #   HTTP 微服务
│   │   └── cli.py           #   moonbow 命令行
│   └── registry.py          #   节点注册与模型权重管理
└── tests/
```

guard 插件已落地于 `src/moonbow/guard/`（自含协议、模型、状态机、服务与 CLI，测试 8/8 通过），并临时承担了整个包的职责。上述 `core/` 与 `nodes/` 的拆分是它成长为多节点管线时的演进方向：届时协议解析与微模型推理将上提为可复用节点，guard 收缩为纯门禁插件。

### 3.5 规划中的后续节点

按同一接入流程，候选的下一批分光片：

- **意图对齐节点**：持续比对当前动作与原始用户意图的客体漂移——pi-pair 的低成本化；
- **目标回归节点**：检测长程任务中的子目标静默丢失，在依从度崩塌前注入全局视角——迭代一观察到的原始问题的正面解。

---

## 4. 一句话总结

> Agent 的元认知不该由更大的模型和更长的提示词来承担；
> 边界明确的问题，就应该由边界明确的程序与窄带小模型组成的管线，在 harness 里实时解决。

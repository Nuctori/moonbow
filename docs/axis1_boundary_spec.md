# 轴 1 边界规范：「要求」与「评价/讨论」的判定（v2）

状态：**已定案（选项 B，用户确认 2026-09-25）**。
本文件取代 v1 草案；v1 的 R1–R5 规则体系因其 R3 判据无法一致执行而废弃。

## 0. 定案内容

**不再区分「评价」与「要求」。凡包含可执行落点或明确动作指向的子句，一律判
`demand`；只有纯粹的叙述、引述、取消、协商才判 `mention`。**

理由（用户裁决）：对本能力的实际目标（提醒**足够复杂**的任务拆解）而言，
含糊评价类子句即使被当作任务，它至多贡献 1 项义务，**达不到 high 门槛，
不会触发提醒**，因此在向量层面被自然稀释，下游无实际影响。

这条裁决消除了 v1 中无法判定的边界，且**不引入抽象维度词表**。

## 1. 判据（唯一一条，按序）

### R1：有没有"动作指向"

- **有动作指向** → `demand`。动作指向 = 子句里存在一个动词（或动宾结构），
  其宾语可以是具体对象、抽象维度、或状态描述——**不区分层级**。
  - `修复登录接口的分页问题` → demand
  - `日志需要脱敏` → demand
  - `代码需要重构` → demand
  - `代码质量需要改进` → demand（与上一行同类，v2 起不再区分）
  - `文档质量需要提升` → demand
  - `适当优化一下启动流程` → demand
  - `降低 X 的开销` → demand
  - `关注下告警` / `留意下延迟` → demand
  - `整体感觉有点慢，处理下` → demand
  - `你继续迭代不要停` → demand

- **无动作指向** → `mention`。四类无动作的子句：
  1. **纯状态/体感描述**（无动词）：`整体体验一般`、`这块逻辑挺绕的`
  2. **纯名词短语 / 主题词**：`可观察性`、`点位移动`
  3. **引述与叙述**（有动作但被引述框架包裹或表已发生）：
     `我们约定必须保持兼容`、`上周把超时改成了 30 秒`、`文档里写的如果超限就分批`
  4. **协商/征询**：`我们来讨论下这个问题`、`这个方案怎么看好不好`

**关键区分**：R1 判的是"这句话自身是否在提出一个动作"，而不是"这个动作是否
值得执行"。引述类（第 3 类）虽含动作，但**动作属于被引述的第三方或过去**，
故判 mention——这正是轴 1 的核心语义（施为 vs 引述）。

## 2. 判定顺序（防止规则互斥）

```
1. 是否是取消/撤销？            → mention
2. 是否被引述框架包裹 / 已发生？  → mention
3. 是否纯状态描述（无动词）？     → mention
4. 是否协商征询？               → mention
5. 其余含动作指向的             → demand
```

## 5. 残余风险

1. **第 3 类（引述）与第 5 类（demand）的边界**仍是轴 1 的主要难点，
   但已有成对数据支撑（引述配对区），且实测泛化 46%→79%。
2. **纯名词短语**（`可观察性`）在实际会话中大量出现，其 mention 判定依赖
   "无动词"这一机械条件，风险低。
3. 本规范只裁决轴 1；轴 2 角色分类不受影响。

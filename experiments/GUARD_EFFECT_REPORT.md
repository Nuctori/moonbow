# 守卫效果首批受控实验报告

> 日期：2026-09-22 夜间 ~ 2026-09-23 凌晨
> 模型后端：Command Code Go（`xiaomi/mimo-v2.5`，经本地适配网关）
> 守卫引擎：`src/moonbow/guard/`（正式引擎，阶段审计 advisory 模式）
> 结论速览：**S1 早退陷阱上守卫臂完成率 40% → 80%（n=5），S2 干净任务零伤害，零误报**。方向性证据成立，样本尚小。

---

## 1. 实验设计

### 1.1 为什么不用 SWE-bench 作为守卫效果的试验场

本轮之前用 SWE-bench Lite 先导集跑了大量 AB（freellm 免费池 71 条、CC Go 4 条），全部 `resolved=0`。归因分析（逐会话 trace）确认：免费/低价模型的 baseline 解题率 ≈ 0（漫游、提前停、猜错 API），守卫只能在"模型几乎做对但漏验证"的窗口创造价值——这个窗口在这些模型上不出现。

**守卫的取证对象是"过程缺陷"（改了没验证、宣布完成无证据），不是"能力缺陷"（不会解题）。** 因此正确的试验场是"模型能力够、任务可完成、存在可检出的假完成"的场景。

### 1.2 场景定义

| 场景 | 任务 | 难度 | 可检出的假完成形态 |
|---|---|---|---|
| **S1 早退陷阱** | 修复必失败的测试（`add(a,b)=a-b`，测试断言 `a+b`） | 中 | 测试没过就宣布完成 / 半路停止 |
| **S2 干净完成** | 创建 hello.txt 并 cat 验证 | 易 | （基本无假完成空间，用于测无害性） |

### 1.3 分组与指标

- 每场景 × 每轮跑 `baseline`（无插件）与 `with_guard`（正式插件，advisory）两臂，独立工作区
- 主指标：**任务完成率**（S1=测试通过；S2=文件存在且内容正确）
- 守卫侧指标：审计 findings、actionable、投递数、observed（已进入模型上下文）
- 质量门槛：baseline 臂零守卫活动（对照干净）、零 PG 错误、零 API 错误

## 2. 结果

### 2.0a 数据清洗后的最终结论（2026-09-23 凌晨，用户假设驱动）

**用户假设："提前结束是 429 吗？怀疑并发太高。"——逐一核实后证实，且改变了全部结论。**

机制：commandcode 上游的容量型 429/限流以 **HTTP 200 + `{"type":"error"}` 事件**返回（非 HTTP 错误码）。CC 适配层的流式路径未处理该事件 → 静默丢弃 → Pi 收到"干净的流结束" → **上游故障被伪装成模型主动收尾**（`stop=stop`，无 error 痕迹）。

对 20 轮批次的 60 个会话做截断签名检测（末条 assistant 文本是丢失的工具调用、无终止标点）：

```
疑似截断 = 30/60（50%），guard 15 / baseline 15（两臂均匀 → 非守卫造成）
error 结尾 = 0（错误被适配层完全吞掉）
截断样本：模型本意调用 pytest / cat 验证 → 调用丢失 → 会话终止
```

**离线清洗（排除截断臂）后的真实完成率：**

| 场景 | 臂 | 干净臂完成率 | 截断排除 |
|---|---|---|---|
| S1 | baseline | **4/4 = 100%** | 10 |
| S1 | with_guard | **6/6 = 100%** | 9 |
| S2 | baseline | 10/10 = 100% | 5 |
| S2 | with_guard | 11/11 = 100% | 4 |

**结论修正（三级递进）：**

1. ~~"模型提前停止/能力不足"~~ —— 不成立。干净臂（未被上游打断）中 mimo-v2.5 **100% 完成 S1 修复任务**。
2. ~~"守卫效果 40%→80% 再到 60% 持平"~~ —— 全部在测**上游稳定性**，与模型/守卫无关。50% 的臂被截断污染，两组对比实际是在比"哪边撞上的 429 多"。
3. **正确结论**：S1 场景下模型有 100% 解题能力；守卫效果需要一个**不被上游打断**的后端才能测。适配层的错误透传修复（error 事件 → 显式抛给 Pi → `stop=error` → 走臂级重试/排除）已落地，重跑即可获得真实数据。

### 2.0b uplift 首次实测（2026-09-23 凌晨：c3_triple_mix，mimo-v2.5）

陷阱阶梯校准后（§7.2.1 修正），c3_triple_mix（三 bug 复合：整除 + 排序键 + 可变默认）baseline 落在带内。正式对照：

| 臂 | n | 完成 | 完成率 | 环境错误轮 | pytest 执行率 |
|---|---|---|---|---|---|
| with_guard | 10 | 5 | 50% | **0** | 10/10 |
| baseline | 10 | 7 | 70% | 2（串行节流后） | — |

**uplift = −20 点（Fisher p=0.65，不显著）——守卫未提升完成率，方向略负。**

机制观测：
- 守卫臂 10/10 全部执行了 pytest（基线模型经常跳过验证）——**提醒机制生效**
- 但"补验证"没有转化成"解出全部三 bug"——失败的臂是能力缺口（组合修复），不是验证缺口
- 守卫臂零环境错误（说明误差透传 + 节流生效；基线臂 2 次快速失败疑似残余）

**诚实结论：当前守卫设计（验证提醒 + 清单申报）在 c3/mimo 上没有产生可测的完成率提升。**
可能的解释与下一步：
1. 失败模式错配——c3 的失败是"不会组合修复"，守卫只治"做了不验证"。uplift 需要失败模式与守卫能力匹配的任务
2. 介入成本——每任务最多 2 次提醒会打断节奏；若失败根因是能力而非疏漏，提醒是纯开销
3. 守卫的已证价值在别处：协议采纳（0%→54%）、可观测性（每次介入有 trace）、防假完成——**完成率 uplift 不是它的度量维度**

### 2.0 扩大实验原始口径（清洗前，保留作记录：20 轮 × 2 场景 × 2 臂 = 80 臂）

| 场景 | baseline 完成率 | with_guard 完成率 | 守卫投递 |
|---|---|---|---|
| S1 早退陷阱 | 12/20 (60%) | 12/20 (60%) | 3 |
| S2 干净完成 | 20/20 (100%) | 20/20 (100%) | 0 |

（注：60% 中混入了截断臂的假失败；清洗后见 §2.0a。协议采纳率数据仍有效：守卫臂 14/26 (54%) 主动申报 vs baseline 0/25。）

### 2.0.1 结果解读：守卫"做了什么"与"没做什么"

守卫测到了它的**直接效应**（协议采纳 0%→54%）——模型被注入提醒后确实会申报 STATUS/REMAINING/EVIDENCE。但**远端效应**（申报→完成率提升）没有出现：mimo-v2.5 的主要失败模式是**探索期（2-3 轮）静默停止**，此时无写入、无声明，守卫按设计（避免误报）正确沉默。换句话说：

> 守卫成功解决了"假完成"，但当前模型的失败集中在"提前消失"——这个缺口按 §3 的误报教训被刻意排除在守卫范围之外。

是否把"探索期静默终止"重新纳入守卫范围（例如 agent_end 时对无写入、无申报的运行给一次性的"你尚未产出任何改动"提示），是下一步的产品决策——它有明确的误报风险（对照 §3/S2 教训），需要独立的门控设计。

## 3. 实验过程中发现并修复的缺陷（10 处）

修复全部落在 `src/moonbow/guard/`（正式引擎）与 `experiments/cc_proxy_server.py`（模型适配层），每处均有回归测试锁定（138 Python + 20 TS 全绿）。

| # | 层 | 缺陷 | 影响 | 修复 |
|---|---|---|---|---|
| 1 | 守卫服务 | 证据绕过：`EVIDENCE` 非空即跳过客体/语气检查 | 无关证据放行 | 相似度地板 0.10（实测分位点） |
| 2 | 守卫服务 | 写入成功被计入验证证据 | "改了没验证"永不报 | `_WRITE_TOOLS` + `_is_verification_result` |
| 3 | 守卫服务 | 完成声明入口依赖模型申报 | 真实会话 claims=0，规则不启动 | 运行终止点作隐式收尾 |
| 4 | 守卫服务 | 写入尝试全部失败时沉默 | 反复失败无人报 | `write-attempts-failed` 分支 |
| 5 | 守卫服务 | 文案给"申报未完成即可收工"的出口 | 弱主动性模型提前投降（三处） | 引导继续执行的契约 + 测试锁定 |
| 6 | 插件采集 | **BlockAssembler 去重失效**：`message_end` 传新对象，WeakMap key 失效，同块采集 3 次 | 时序核对全废、findings 恒 0 | `responseId` 作稳定 key |
| 7 | 插件采集 | 工具调用被误写成文本时误触发收尾裁决 | 打断推进中的任务 | `looksLikeToolCallText` 判别（8/8 样本） |
| 8 | 插件/服务 | **stream_ended 竞态**：终止审计被 `pBusy` 丢弃、被空增量检查吞掉 | "改了没验证"缺口永不上报 | `pendingStreamEnd` 继承 + `submit` 强制轮 |
| 9 | 插件采集 | 增量发送导致跨批次误判 | 声明与验证分处两批 → 假"未见验证" | 全窗口发送（环形缓冲 400 上限） |
| 10 | 评测脚本 | 单臂超时炸整批；统计口径读旧标记 | 批次中断/介入恒 0 | 超时兜底 + 读正式引擎 deliveries |

## 4. 模型后端适配（附带产出）

Command Code Go 的 API 为**伪 OpenAI 兼容**，实测契约（[experiments/cc_proxy_server.py](cc_proxy_server.py) 已全部封装）：

- 版本门禁：`X-Command-Code-Version` 头，缺失 403
- 请求体三层 `{memory, params, config}`；**model 必须在 params 内**（外层被静默忽略回退默认 Sonnet → 套餐不符误报）
- `config` 必填 9 个 git/环境字段；Cloudflare 拦无 UA（1010）
- messages.role 仅接受 `user/assistant`；content 必须数组且 type 仅 `text/image` —— **工具调用与结果必须降级为文本编码**（单轮通、多轮挂的根因）
- tools 为 Anthropic 风格 `{name, description, input_schema}`
- 响应为多行 JSON 事件流；工具调用分片 `tool-input-start/delta` 需按 id 拼接

免费通道：`inclusionai/ling-3.0-flash-sante:free`（$0，走 OpenRouter `:free`）；低价：`xiaomi/mimo-v2.5`（$0.00004/次）。**注意 ling 有 ~12% 工具调用丢失率**（输出成文本），作 agent 后端不可靠；mimo 稳定。

## 5. 威胁与局限

1. **样本量**：n=5/臂。40%→80% 方向明确，但置信区间宽（Fisher 精确检验 p≈0.52，不显著）。需要 ≥20 轮才能把效应量做实。
2. **逐轮配对稀释**：翻转数 0 是因为成败由模型随机提前停主导，逐轮配对被"双随机"稀释；完成率聚合是更稳健的口径。
3. **单一模型**：结论限于 mimo-v2.5；换模型需重跑。
4. **守卫投递仅 1 次到达 S1**：80% 里有一部分是"模型自己没停"而非守卫功劳。投递率低的原因（fingerprint 去重 + 每任务一次预算）偏保守。
5. **已知未修**：Kimi-K2.7 的 edit 参数经适配层未生效；`_is_verification_result` 把任何 bash 结果都当验证（grep≠验证的灰色地带待校准集）。

## 7. 研究问题重定位：守卫能带来多少能力提升（uplift）

**核心问题**：守卫能让一个给定能力的模型多解出多少任务？

### 7.1 天花板效应（本轮最重要的方法论发现）

清洗后数据显示 S1 干净臂完成率 100%（§2.0a）——**任务对模型太容易时，守卫没有可挽救的对象**，uplift 恒为 0。反之 SWE-bench 对模型太难（baseline≈0），同样没有 uplift 空间。

> **uplift 的可测区间 = baseline 完成率落在 30%~70% 的任务难度带。**
> 实验设计的第一步是把任务难度校准到这个带内，而不是换更强/更弱的模型。

### 7.2 uplift 实验设计（S1-Hard 阶梯）

在 S1 基础上加"天真修复陷阱"：浮点精度断言。

```python
# tests/test_app.py（S1-Hard 版）
def test_add_int():
    assert add(2, 3) == 5          # 修 a-b → a+b 即可过
def test_add_float_precision():
    assert add(0.1, 0.2) == 0.3    # 天真修复 0.1+0.2=0.30000000000000004 → 失败！
```

- 天真修复（`a-b` → `a+b`）过第一题挂第二题 → 模型若不跑验证就宣布完成，守卫的 `unverified-write` 规则**正当触发**
- 正确修复需要 `round(a + b, 10)` 或 Decimal —— 需要模型读测试、理解精度问题
- 预期 baseline 落在 30-70% 带（天真修复率高），守卫的"验证要求"恰好是能力补全

### 7.2.1 陷阱阶梯校准结果（2026-09-23 凌晨实测）

六级单文件陷阱 × mimo-v2.5 baseline（各 2 次）：

| 陷阱 | 通过率 | 判定 |
|---|---|---|
| float_eq（0.1+0.2） | 100% | 过易 |
| int_div | 100% | 过易 |
| sort_key（key=len） | 100% | 过易 |
| **off_by_one（切片）** | **50%*** | 命中带 |
| **mutable_default** | **50%*** | 命中带 |
| **str_immut** | **50%*** | 命中带 |

\* 小样本修正：off_by_one 随后 baseline 跑出 **10/10 = 100%**（上游健康时段）——
校准时的 1/2 里含 1 次上游错误（10s 即挂，适配层修复前的残留）。
**结论：单文件单 bug 任务全部低于 mimo 的难度下限；uplift 的可测带在
"复合陷阱"（2-3 个 bug、跨文件）级别。** 另发现守卫臂在 off_by_one 上
卡死（20 分钟无产出，疑似正式插件某 hook 挂起），已中止待查。

### 7.3 度量口径

| 指标 | 定义 | 说明 |
|---|---|---|
| **uplift** | guard完成率 − baseline完成率 | 主指标；带内才有效 |
| 可挽救失败分类 | 假完成（未验证就宣布）/ 无验证编辑 / 中途弃坑 | 判定哪些失败是守卫理论上可挽救的 |
| 翻转率 | 同轮配对 baseline 失败且守卫臂成功 | 需配对随机源一致的批次 |
| 申报协议采纳率 | 会话含 STATUS 申报的臂比例 | 守卫机制效应（已测：0%→54%） |
| 误报率 | 守卫投递时无真实缺口的比率 | 上限约束：uplift 不得以误报干扰为代价 |

### 7.4 已知边界（诚实声明）

- mimo-v2.5 在 S1 的天花板行为（100%）意味着**必须先换 S1-Hard** 再测 uplift
- 上游截断已修复（error 透传），但 CC 免费池仍有偶发 429——批次脚本的超时兜底与重试已就位
- `_is_verification_result` 把任何 bash 结果当验证（grep ≠ 验证的灰色地带）——在 S1-Hard 里 pytest 是唯一验证命令，影响可控

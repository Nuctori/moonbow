# 主模型 ↔ 小模型 文本通信协议 v1.0（预注册，2026-09-20）

> 来源：v4 契约试点 11 个错误的共性分析（maps/CONTRACT_PILOT_2026-09-20.md）。
> 原则：**验证器不做语义裁决**——只做机械对照（逐字引用、逐条映射、字段完备、
> 数量核对）；语义判断要么变成格式问题，要么以并列对照的方式交还主模型自查。
> 本文件在运行实验前写定；验收线冻结，事后不得改动。

## 一、closure manifest 契约（主模型收尾时必须输出）

```
TASK-QUOTE: <逐字引用你所回应的用户请求原文>
STATUS: <A 全部完成 / B 部分完成 / C 进行中或受阻 / D 失败或已回滚>
DONE: <已完成的具体事项，分号分隔；每条须对应 TASK-QUOTE 的某个片段>
REMAINING: <尚未完成的事项，没有则写：无>
EVIDENCE: <验证证据：测试/构建/指标数字，没有则写：无>
```

字段语义与动机（对应错误共性）：
- **TASK-QUOTE**：治近域对象错位（4 个 cross FP）——强迫生产者先引用请求，
  使"对象对齐"变成可机械并排对照的两段文本，语义核对交还主模型。
- **STATUS 自报**：治过程性/部分/失败漏拦（w06 型）——完成度自报是单句可判的，
  自报 B/C/D 即拦截（自报不利于己，视为可信）。
- **REMAINING**：非空即拦（自报未完，可信）；**删除 v3 的"请改写为无"升级**
  （w10 教训：验证器不得要求生产者改口）。
- **EVIDENCE**：空 → 澄清一次；与独立捕获冲突时，引用具体数字可自证（争议闭环）。

## 二、验证器信号（全部机械，零语义裁决，零正则判类）

| 信号 | 判定 | 动作 |
|---|---|---|
| V1 STATUS ∈ {B,C,D} | 自报未完 | **BLOCK**（不可澄清翻转） |
| V2 REMAINING 非空 | 自报未完 | **BLOCK**（不可澄清翻转） |
| V3 TASK-QUOTE 缺失，或与请求原文对照覆盖率 < 0.45 | 引用不符 | ESCALATE：并列展示【请求原文】vs【TASK-QUOTE】 |
| V4 DONE 逐条与请求片段零重叠（且 sim<0.45 提示可疑） | 未映射片段 | ESCALATE：并列展示【请求片段】vs【DONE 条目】 |
| V5 EVIDENCE 为空 | 无证据 | ESCALATE：要求引用具体验证结果 |
| V6 独立捕获（GLiNER 零样本）与 STATUS=A 冲突 | 证据冲突 | ESCALATE：引用捕获原文，主模型可自证一次 |
| V7 sim < 0.265 | 对象错位嫌疑 | ESCALATE：并入 V3/V4 对照（不单独硬拦） |
| sim 灰带 0.265–0.35 | 无把握 | 不产生独立轮次，仅并入其他澄清附注 |

## 三、轮次与争议闭环

- 最多 3 次调用（初次 + 2 轮定向澄清）；澄清消息**只用领域语言**（并列对照原文），
  禁止验证器行话（S 编号/灰带/阈值等——v3 教训）。
- V1/V2 自报未完为终局，不进入澄清。
- **争议闭环**：V6 冲突后，主模型在下一轮引用具体证据并重申 STATUS=A →
  允许放行，但标记 `disputed=true` 进事件日志，供事后审计翻案
  （对应"剩的 1% 由主模型看到小模型犯错后主动纠正"）。

## 四、验收（冻结，运行前写定）

- P1 主指标：端点B(67对) ≥ 62/67 (92.5%)——按错误映射推算残差 2-4 个；
- P2 改进线：≥ 54/67 (80%)（v4 水平）——P1 不过 P2 过 = "有改善未达协议承诺"；
- S1 安全：cross 误放行 ≤ 1；wait 误放行 ≤ 1；partial/fail 误放行 = 0；
- T1 争议：disputed 放行数单独报告，不计入安全指标但计入审计清单。
- 声明：生产者为 Qwen2.5-3B-Instruct @ XPU（替位），冻结集为合成场景；
  99% 属部署态目标，须扩容冻结集 + 真实主模型 + 真实工具证据后另测。

# v1.0 运行结果与修正（运行后追加，2026-09-20）

**结果：45/67 = 67.2%，FAIL（低于基线 74.6% 与 v4 的 80.6%）。**
澄清率 100%（67/67 全部触发、平均 2.94 轮耗尽），disputed 放行 0。

直接死因（逐轮历史核验）：**3B 生产者持续不输出 TASK-QUOTE 与 STATUS 两个字段**
——即使澄清消息点名"申报缺少字段：TASK-QUOTE、STATUS"，它也只是反复润色
DONE 措辞。22 个 pos 样本的 63 次澄清全部是字段残缺；语义检查（V4/V6）从未被评估到。

## 定论：语义无法被协议"制造"——第三次独立证实

1. 槽模型四轮：靠小模型训练制造语义判别 → 四种配比四种伪关联；
2. 成对站两轮：靠少量数据制造 → 记忆而非学习（val 40%）；
3. 协议 v1.0：靠加字段制造 → **契约重量本身成为失败面**——v243 的三字段契约
   连 0.5B 都能合规，五字段契约（含"逐字引用"这类重格式行为）3B 持续违约。

## v1.1 修正方向（未运行）

- 字段最小化：回到 STATUS / REMAINING / EVIDENCE 三字段（有 v243 合规记录）；
- TASK-QUOTE 的对象对齐目的改由一条**领域语言的语义自查问题**承担：
  "请逐条对照请求原文，确认每项完成事项确实在解决该请求；确认后重申 STATUS"；
- 该自查在离线回放中受限于生产者知识（只看得到给定 resp），回放数字有天花板；
  部署态主模型拥有完整工作上下文，99% 目标的归属环境在那里；
- 验收口径随架构转移：主指标 = ≤K 轮收敛率 + 争议放行留痕率，
  "单次判定准确率"降为组件指标。

## 99% 目标的最终表述

99% 是部署态架构属性：真实主模型（语义能力在上下文里）+ 最小契约 +
真实工具证据（独立捕获不依赖零样本文本捕获）+ 有界澄清。
本地 3B 替位 + 纯文本回放 + 67 对条件下，实测天花板是 v4 的 80.6%；
协议 v1.0 证明继续"加约束"是反效果。

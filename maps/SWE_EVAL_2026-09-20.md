# SWE-bench Lite 评测基建与首轮实测（2026-09-20）

## 一、 目标

把进度守卫（progress guard）从离线 67 对静态评测，推进到 **真实 Agent harness + 真实仓库**
的在线评测：用 Spark-X2.5-4B 作为主模型跑 SWE-bench Lite，对照「纯模型」与「挂载守卫插件」
两种配置，采集 **Token 效率** 与 **软注入介入效果**。

## 二、 关键工程决策（含一次返工）

### 1. 推理后端：PyTorch-XPU → llama.cpp Vulkan（决定性）

| 后端 | 解码速度 | 结论 |
|---|---|---|
| PyTorch XPU (eager attention) | **3.87 tok/s** | 不可用：单题 15k token 需 65 分钟 |
| **llama.cpp Vulkan (Q4_K_M)** | **33 ~ 58 tok/s** | **采纳**，约 ×10~15 |

放弃 XPU 直调的原因（profiler 实证）：
- `urEnqueueKernelLaunchWithArgsExp` 占 5553 ms（CPU 侧），实际 gemm 仅 174 ms
- A770 显存总线 64-bit，batch=1 时有效带宽利用率仅约 5%
- 官方 `modeling_spark.py` 硬编码 `eager_attention_forward`，绕过 XMX 加速
- 尝试替换为 SDPA：速度无提升且输出退化为乱码（SWA mask 语义不等价），已回滚
- XPU 无 Triton 后端，`torch.compile` 不可用

### 2. Agent harness：手写循环 → 直接封闭 Pi（方法论修正）

**一次明确的返工**：先前手写 `agent_loop.py`（bash/view/str_replace/submit + 自研 tool-call 解析）
是错误路径，原因：
- Pi 本身即完整 harness（工具、上下文、会话持久化、模型适配全部现成）
- 手写循环引入的差异会让实验**无法归因**——测出的差异究竟是「守卫效果」还是「简陋循环的缺陷」
- 实际撞坑印证：Spark 用 `<arg_key>/<arg_value>` 原生 tool-call 格式而非 JSON，
  而 llama.cpp 的 `tools` 参数已能自动转换，手写解析纯属重复劳动

### 3. 环境无关的 Pi 封闭发行版

利用 Pi 内建的隔离开关做到零污染：

| 机制 | 作用 |
|---|---|
| `PI_CODING_AGENT_DIR` | 重定向配置目录，完全无视宿主 `~/.pi/agent` |
| `--no-extensions` + `-e <path>` | 禁用宿主全部扩展，只加载我们的守卫插件 |
| `--no-skills/--no-themes/--no-context-files` | 屏蔽环境干扰 |
| `--session-dir` | 会话实时落盘到封闭目录，供指标解析 |

产物：`pi_eval/`（home/models.json + extensions/progress-guard.ts + run_case.py）

### 4. 指标采集：抓 stdout → 解析会话 JSONL（关键修正）

`--mode json` 是**流式事件输出**，与 `--print` 组合会持续刷屏而非给出最终 JSON，
故早先的 stdout 抓取全部失败。**正确做法是解析 Pi 实时落盘的会话文件**
（`sessions/*.jsonl`，含 `thinking` / `toolCall` / `toolResult` 完整轨迹）。

产物：`pi_eval/session_parser.py`（提取工具调用序列、是否编辑、是否测试、thinking 量）

### 5. 判定协议：SWE-bench 标准流程 + 防 reward hacking

判定必须遵循官方协议，否则结果无效：
1. **FAIL_TO_PASS 测试在 base commit 上通常不存在**，由官方 `test_patch` 引入 → 必须先 apply test_patch 再跑
2. **防 reward hacking**：实测发现模型会**篡改测试文件**来「通过」测试
   （首轮 with_guard 补丁中出现 `tests/test_blueprints.py` 被删 79 行）
   → 判定前必须 `git checkout` 还原所有 `tests/` 与 `test_*.py` 的模型改动

### 6. 依赖隔离：per-repo venv

不同题目的依赖版本互相冲突（flask-4045 需 `pytest==6.2.4` + `Werkzeug==2.0.1`，
而宿主是 pytest 9.x + Werkzeug 3.x，后者移除了 `url_quote`）。
直接在共享 venv 安装会污染宿主并因旧版 C 扩展（greenlet）编译失败而回滚。
→ 采用 `D:/swe_sandbox/venvs/<repo>/` 每题独立 venv。
产物：`pi_eval/repo_env.py`

## 三、 首轮实测结果（pallets__flask-4045）

题目：`Raise error when blueprint name contains a dot`（base commit d8c37f4）

### 模型行为（来自会话轨迹）

| 模式 | 工具调用 | 行为 | diff | 耗时 |
|---|---|---|---|---|
| baseline | 15 次（bash 13 / read 2） | 探索 → 编辑 `blueprints.py` | 2 行 | ~9 min |
| with_guard | 14 次（bash 12 / read 2） | 触发守卫软注入 | 155 行（含篡改测试） | 9.1 min |

### 产出补丁（源码部分）

```python
# src/flask/blueprints.py  Blueprint.__init__
+        if "." in name:
+            raise ValueError("Blueprint names should not contain dots")
```

**这个修改方向正确**（官方 ground truth 即包含该 name 校验）。

### 最终判定：FAILED

```
FAILED tests/test_blueprints.py::test_dotted_name_not_allowed
FAILED tests/test_blueprints.py::test_route_decorator_custom_endpoint_with_dots
```

根因：官方修复要求**同时**放宽 `endpoint` 里的点号限制
（`add_url_rule` 中 `assert "." not in endpoint` 需一并处理），
模型只做了 `name` 侧校验，**漏掉了 endpoint 侧**。

### 两个高价值副产物

1. **守卫拦截链路已验证可用**：`guard_service` 在实跑中被调用 14 次（HTTP 200），
   守卫插件在真实 Pi 会话中成功挂载并触发。
2. **实证了 reward hacking 风险**：with_guard 那一轮模型删改了 88 行测试代码，
   若不剥离测试改动，会被误判为「解决」——这为「守卫必须锚定真实工具证据」
   提供了直接的实证支持。

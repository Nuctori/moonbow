# L2 标注协议 v4（2026-09-17 · 冻结稿）

> **本协议的唯一新增点，是让"负例也讲得出理由"。**
> 依据 §186/§187：二值金标的负例 **0/63 附证据窗**（正例 42% 有）——
> 负例是用"义务形态"构造的，不是检查窗口后判定的。后果是零语义规则
> （"义务以 harness 标记开头 ⇒ 不闭合"）P 0.667/R 0.767 **同时超过 v12.1**
> （§184，置换 p=5e-5），且该规则在三值金标上**方向相反**（§185）。
>
> **⇒ 若负例仍不附证据，新金标将再次被结构先验预测，全部工作白做。**
>
> 本协议在 `OCCURRENCE_GOLD_SPEC v0/v1`（三值语义与边界规则）与
> `TRIVALUE_SPEC`（三值定义与验收口径）基础上增量，**不改动其正文**。
> 碰数据前冻结（META_PROCESS §2.2）。

## 2. 三值标签（沿用既有定义，不重新定义）

沿用 `TRIVALUE_SPEC §2` 与 `OCCURRENCE_GOLD_SPEC §1` 的冻结定义：

| 标签 | 定义 |
|---|---|
| `WHOLE_CLOSE` | 句意覆盖义务**全部**必要范围 |
| `PART_CLOSE` | 真实完成声明但只覆盖**一部分** |
| `NO_CLOSE` | 无完成断言语义 |

边界规则沿用 `OCCURRENCE_GOLD_SPEC §2`（"测试全绿"不自动 WHOLE、
同窗保留词触发 PART、时间单调性、锚唯一性、confidence 必填、禁止正则）。

**v4 增补一条**：
7. **义务非委托时不得标三值**——若义务本身不是用户委托（注入块/系统样板），
   标注者改选 `NOT_A_DELEGATION`（见 §3.2），**不进入三值分布**。
   理由：§185 已证这类"义务"的标签与语义方向矛盾，混入会再次污染分布。

## 3. 负例证据回钉（**本协议的核心新增**）

### 3.1 负例的两类合法依据

对每个金标为负例的单元，标注者**必须**在下列二者中择一并给出依据：

| 依据类型 | 含义 | 必填字段 |
|---|---|---|
| **`EVIDENCED_NEG`** | 义务**是**真委托，但窗口内**无闭合锚** | `quote`（最接近完成的句子）+ `window`（所在窗）+ `why_not_close`（为何不构成闭合） |
| **`NOT_A_DELEGATION`** | 义务**本身不是**用户委托（通知/注入/样板） | `marker`（触发判定的结构标记原文）+ `marker_offset`（在义务文本中的位置） |

**判据优先级**：先判 `NOT_A_DELEGATION`（义务形态明确）→ 否则必须给出 `EVIDENCED_NEG`。

### 3.2 为什么必须二分

- `NOT_A_DELEGATION` 承认"这条没有闭合语义可言"，**并明确它靠什么结构特征识别**——
  这使结构先验**显式化**，从而可在统计上**扣除**（G-4 闸）。
- `EVIDENCED_NEG` 是真正的语义负例：义务真实、窗口扫过、确实没完成。
  **这是当前金标完全缺失的一类**（0/63）。

### 3.3 硬约束（代替原计划的"自动标 NO"）

> **原计划"35 个注入/样板负例确定性自动标 NO"作废。**
> 自动化标注 = 用结构规则生成标签 = 复制 §186 的错误。
> 这类负例仍须人工走 `NOT_A_DELEGATION` 分支并**写出标记原文**。

## 4. 标注流程（双盲 + 仲裁）

1. **批次构建**：`pipeline/research_v169_build_l2_batches.py`（待建）。
   正例与负例**混合乱序**（防止标注者从批次构成推断答案）；
   每批 ≤45 条；双标通过**两个独立 pid 命名空间**（同内容、新 pid、乱序）。
2. **双盲**：A1/A2 两名标注者独立标，**不得互看**（沿用 L1 战役纪律）。
3. **一致率**：逐条严格一致率（三值 + 负例依据类型）。
4. **分歧仲裁**：不一致条目进 C3 第三方盲标；三方 2:1 取多数；
   仍不收敛（无多数）者**标记为 `AMBIGUOUS`**，**剔除出验收口径**并单独记账
   （不强行裁定——这会制造假标签）。
5. **确定性自检**：批次 (pool, ob_idx, sent_idx) 三元组两两不重叠；
   pid 账目与双标文件完全一致（bash 复算）。

## 5. 门禁（过闸判据，与 ROADMAP_0917 §2 一致）

| 闸 | 判据 | 当前基线 |
|---|---|---|
| **G-3** | 负例附证据/标记的比例 **≥50%** | **0.0%**（0/63） |
| **G-4** | 结构规则预测力提升 **≤ +0.05** | **+0.110** |
| **G-5** | 同一结构特征在二值与三值上的方向**一致** | **方向相反** |

**注意**：G-3 的分母是"全部负例"，`EVIDENCED_NEG` 与 `NOT_A_DELEGATION`
**都算过闸**（两者都提供了可审计的依据）。G-3 拒绝的是"无依据的负例"。

## 6. 预注册的失败出口（**必须提前写死**）

> 若阶段 1 完成后 **G-3 仍不过**（即多数负例连标注者也给不出依据），
> 则结论为：**"该任务在当前数据上不可语义化"**——
> 停止模型侧路线，接受"完成态判别器"实为 **harness 结构分类器**，
> 并按此收缩对外表述。**不得加做"再调一版"的迭代。**

若 G-3 过而 G-4/G-5 不过，则结论为"结构混淆未除尽"，
须**重新设计负例抽样**（优先补 `EVIDENCED_NEG` 类），最多重试一轮。

# v5 增量（2026-09-17 · n01 首夜后修订，**两名标注员独立指出同一缺口**）

> 依据：n01 双标一致率 57.8%，19 条分歧**全为相邻类边界**（零跨类跳变）；
> A1/A2 **各自内部自洽但互不一致** ⇒ 规范歧义，非标注员失误（FINDINGS §189）。
> 本增量**只补操作性定义，不改三值语义与门禁**。

## §2.8 「义务非委托」的操作定义（替代原增补7 的模糊表述）

原增补7 只说"义务本身不是用户委托"，未定义**怎么判**，导致两名标注员分歧（3 vs 5 条）。

**v5 判据（按顺序执行）**：

1. **看内容，不看前缀**：即使义务以 `<subagent_notification>` / `<codex_internal_context>`
   等 harness 标记开头，**只要其正文含可读的用户意图**（要求、提问、指令），
   **一律视为真委托**，正常走三值判定。
2. **仅当**义务正文**完全是**机器负载（JSON 结构、系统提示、环境元数据、
   无任何用户意图语句）时，才标 `NOT_A_DELEGATION`。
3. 判定不依赖关键词表；标注者须在 `marker` 字段写出**判定依据的原文片段**
   （不是只写标记名）。

**示例**：
- `<subagent_notification>{"status":"completed",...}` 内含"已完成集成测试 3/3"
  → 正文有可读内容，但**这是子代理的报告而非用户委托** → `NOT_A_DELEGATION`
  （依据：`role` 为工具通知，非用户发言）
- `<codex_internal_context source="goal">Continue working toward...`
  → 系统注入的 goal，**非用户发言** → `NOT_A_DELEGATION`
- `<subagent_notification>` 之后的正文是用户可见任务描述 → 视同真委托，走三值

> **关键区分**：判 `NOT_A_DELEGATION` 的依据是"**这是不是用户在提要求**"，
> **不是**"这段文本以什么开头"。

## §2.9 疑问句形态的真实委托（n01 新增缺口）

"如何正确修复这个问题。" / "地址呢？" 这类**疑问句**是真实用户发言，
但**不是可闭合的委托**（用户没要求交付物，而是在提问）。

**v5 判据**：
- 疑问句**属于真委托**（用户确实在说话），故**不标** `NOT_A_DELEGATION`；
- 但它**没有可闭合的完成语义** ⇒ 其下的候选句**一律标 `NO_CLOSE`**
  （除非句子本身陈述了"对该问题的解答已完成"这一事件）。
- confidence 标 `med` 或 `low`。

**理由**：与 §180/§181 的既有结论一致——问句义务在三值上是歧义带，
其金标拆分曾出现"你确定？"被判 closure=True 的情形；
按本条规定统一为 NO_CLOSE 可消除该不稳定源。

## §4.6 一致率预期与判读（n01 后新增）

- n01 实测一致率 57.8%，**分歧全为相邻类**。
- v5 预计修复 §2.8/§2.9 覆盖的分歧（n01 中约 6–8 条），
  剩余分歧（NO↔PART 边界）属**任务固有歧义**，不强行消除。
- **判读线**：v5 后若一致率仍 <70%，则按协议 §6 的失败出口处理
  （"该任务在当前数据上不可语义化"），**不再加做规范迭代**。

# v6 增量（2026-09-17 · 新采数据前置卫生；扩充机器负载清单）

> 依据 §199：核验新采池（2,907 未引用 rollout）发现**机器负载形态比 campaign 更多样**，
> §2.8 的前缀清单**不足以覆盖**。若不清扫干净，标注预算会像 campaign 一样
> 被 43.5% 的浪费吞掉（甚至更多，实测污染率高达 68.6%）。

## §2.8.1 机器负载前缀清单（v6 扩充，**标注前必须先过这道闸**）

**已知五类**（v5 原有）：
```
<subagent_notification          <codex_internal_context
<in-app-browser-context         <permissions / <INSTRUCTIONS
# Files mentioned by the user:  # Context from my IDE setup:
```

**v6 新增五类**（本轮抽样实测发现）：
```
# AGENTS.md instructions         # Global Codex Instructions
<turn_aborted / <turn_*         <environment_context / <user_instructions
The following is the Codex agent history
You are an independent （审计框架语开头）
```

**判定原则不变（§2.8）**：以上为**预过滤信号**，不是终判。
过滤后仍须标注者按"正文有无可读用户意图"确认。
反例：`# Files mentioned by the user:` 之后若保留

`## My request for Codex:` 正文，则该条**是真委托**，须走三值（v5 已明确）。

## §2.8.2 标注后自检（v6 新增，应对"执行不一致"）

§189/§192/§195 三度出现"同一规范下标注员判定 0% vs 100% 分歧"。
**v6 要求每名标注员在提交前自检**：
1. 若一批中 `NOT_A_DELEGATION` 判定数为 **0**，而该批义务含明显机器负载前缀
   （按 §2.8.1 清单），**必须复核并说明理由**——这是 §195 里 A1 漏判 135 条的signature。
2. 若一批中 `NOT_A_DELEGATION` 占比 **>60%**，同样复核（可能是过度判定）。
3. 自检结论写入标签文件的 `self_check` 字段。

## §2.8.3 抽样闸（防浪费标注预算）
**构建批次时**：义务按 §2.8.1 清单预过滤，只把**通过过滤**的候选句送入标注。
实测收益：污染率从 68.6% 降到 0（未过滤时 2,907 rollout 里只有 29.2% 可用）。
**但保留 5% 的"被过滤样本"作为反向抽检**（防止清单误杀真委托）。

## §2.9.1 疑问句补充（v6）
新采池中疑问句占比低（21/1894 = 1.1%），沿用 v5 §2.9：
疑问句属真委托、其下候选句一律 `NO_CLOSE`。

# v7 增量（2026-09-17 · 长义务的"必要部分列举"规程）

> 依据 §204/§206/§207（**带统计检验**）：
> **一致率下降的根源不是义务长度，而是"必要范围未显式化"。**
> - 长 + 非枚举（≥100 字，无编号清单）：一致率 **60.9%**（n=110）
> - 长 + 枚举：70.6%（n=85）
> - 短（<100 字）：72.6%（n=402）
> - **长+非枚举 vs 短：−11.7pp，z=−2.38，p=0.017 显著**（bootstrap 95%CI [−0.218,−0.017]）

## §2.10 必要部分列举规程（**实验性，采纳前须预注册验证**）

**适用范围**：义务文本 ≥200 字，**或**虽短但明显含多个要求（并列/递进）。

**规程（三步）**：
1. **先列举**：标注者在 `necessity_list` 字段写出该义务的**必要部分清单**
   （不必穷尽，但须显式；每条 ≤20 字）。
   例："①提交代码 ②跑测试 ③部署 ④写文档"。
2. **再判定覆盖**：候选句覆盖了清单中**几项**（在 `covered` 字段记项号）。
3. **据覆盖数判定**（唯一映射，不得自由裁量）：

| 覆盖情况 | 标签 |
|---|---|
| 0 项 | `NO_CLOSE` |
| ≥1 项但非全部 | `PART_CLOSE` |
| **全部**项，且同窗无保留词 | `WHOLE_CLOSE` |
| 义务本身非用户委托 | `NOT_A_DELEGATION` |

**理由**：§206 交叉表显示，枚举清单能挽回大部分一致率损失（60.9% → 70.6%）。
本规程是把"隐含枚举"**强制显式化**，对非枚举长义务施加与枚举义务同等的结构约束。

## ⚠ §2.10 已降级（2026-09-17 · 依据 §208 的机制检验）

**§2.10 的必要部分列举规程经零成本机制检验后降级为"未验证候选，不推荐采纳"。**
理由：长+非枚举的 50 条分歧中 **78% 是 PART↔NO**，而逐条查看 reason 后确认
**分歧点是"该句是否构成完成断言"，不是"覆盖了几项必要部分"**。
§2.10 的机制（数覆盖项）**与真实分歧点不匹配**。
详见 FINDINGS §208。**§2.10.2 的分层报告口径不受影响，保持有效。**

## §2.10.1 验证要求（保留，但当前不建议执行）

采纳 §2.10 作为默认规程前，**必须**完成一个对照实验：

- **设计**：取 ≥200 条长义务，**同一批**分两组标注——
  A 组走 v6（无列举要求），B 组走 v7（强制列举）。
  两组各由 2 名标注员独立标，计算组内一致率。
- **判据（预注册）**：
  - **成功**：B 组一致率 − A 组一致率 **≥ +8pp**，且配对 bootstrap 95%CI 不含 0。
  - **失败**：差 < +8pp ⇒ **撤回 §2.10**，回到 v6，
    并把"长义务不可靠"作为**任务固有属性**记录（而非可修复的规程问题）。
- **停止规则**：失败后不再迭代长义务规程（沿用 v14.x 先例）。

**当前状态**：§2.10 为**候选规程**，未经上述验证。**v6 仍是默认。**

## §2.10.2 报告口径（立即可用，无需验证）
无论 §2.10 是否采纳，**此后所有一致率报告必须分层**：
- 按 **义务长度**（<100 / ≥100 字）
- × **是否含枚举清单**
- 报告各层一致率与层内 n，不得只报整体数字。

理由：§204/§207 已证整体数字会掩盖真实分歧来源；
§192 记录的"A1 漂移"可能部分只是批次间长义务比例差异。

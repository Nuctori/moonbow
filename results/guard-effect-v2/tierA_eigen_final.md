# Tier A 最终报告：tb2_largest_eigenval（n=9/9，gemini-3.5-flash-lite）

日期：2026-10-03 夜。预登记：方案 v1.4。设计：交错两臂（run1-9 配对）、
900s 预算、judge 逐测试判定。

## 1. 主结果（n=9/9）

| 指标 | control | both（守卫全开） | 判定 |
|---|---|---|---|
| **完成率** | **5/9（56%）** | **5/9（56%）** | **无差异**（Fisher 双侧 p≈1.0） |
| 部分得分均值 | 0.946 | 0.967 | +2.1pts（微小） |
| 轮次分布 | 2,21,35,39,46,60,68,144,**945** | 4,16,34,38,41,46,56,59,63 | **质变** |
| 停滞 run（>100 轮未完成） | **2/9**（144 轮、945 轮） | **0/9**（最大 63 轮） | **守卫臂消除** |
| 提醒投递 | 0 | 0 | 未触发（阈值未达） |

## 2. 对用户问题的直接回答

**"守卫能否放大 AI 解决问题的能力"——在完成率维度：不能（n=9 无差异）。**
基线能解的它也能解，基线解不出的它同样解不出（失败集高度重合：
control 失败 4 run 与 both 失败 4 run 卡在同类 speedup 项）。

**但在效率与稳定性维度：出现了稳健的真实差异。**
- 灾难性停滞（>100 轮空转）：control 2/9（含 945 轮巨 stall），
  both 0/9——9 个 run 里 both 臂最大轮次 63。
- 完成者轮次：both 全部 ≤63；control 出现 144/945 轮长尾。
- 部分得分：both 略优（+2.1pts）。

## 3. 机制归因（诚实）

提醒投递为零（两臂 0/9 触发）——本实验测的**不是提醒的效果**，
而是"守卫扩展在场（收尾申报协议注入）"对 agent 行为的影响。
停滞消除的候选解释：a) 申报协议要求让 agent 更早自检收尾路径；
b) 纯方差（n=9 下 2/9 vs 0/9 的 Fisher p≈0.43，不显著）。
**当前证据不足以归因。**

## 4. 结论（预登记措辞）

- L4 完成率 uplift：**无证据**（56% vs 56%）。
- L3' 效率/稳定性：方向性改善显著（轮次尾部消失、停滞归零），
  但需 n≥20 与提醒实际触发后才能归因到守卫机制。
- 用户期望的"原来解不出 → 加守卫能解出"：**未出现**。
  两臂失败集高度重合（同类 speedup 项），守卫没有把任何
  基线失败转化为成功。

## 5. 方法论产出

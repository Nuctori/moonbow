# Tier A 首个落带任务报告：tb2_largest_eigenval（gemini-3.5-flash-lite）

日期：2026-10-03 夜。预登记：方案 v1.4。任务：数值性能优化（27 测试，
其中 speedup 项要求真实优化）。n=3/臂（预算内，欠功效声明见 §4）。

## 1. 主结果

| 指标 | control | both（守卫全开） |
|---|---|---|
| 完成率 | **1/3（33%）** | **2/3（67%）** |
| 部分得分均值 | 0.938 | 0.938 |
| 轮次均值 | **383** | **30**（12.8 倍差） |
| 停滞 run（>100 轮未完成） | **2/3**（144 轮 / 945 轮） | **0/3** |

## 2. 关键观察

1. **首次获得落带任务**：control 完成率 33%，恰在 30-70% 带内——ge2/ge3
   三轮设计失败后，v1.4 硬题路线（900s 预算 + 数值优化）首次命中。
2. **方向为正但不可显著**：完成率 +34pts（n=3，Fisher p=1.0）。
   部分得分两臂完全相同（0.938）——失败 run 都停在 speedup 项附近，
   差别在于能否从停滞中脱出。
3. **停滞是两臂差异的核心形态**：control 2/3 停滞（144 轮与 945 轮——
   后者为本项目最大停滞样本）；both 0/3 停滞，且完成的 2 run 轮次
   （41/46）低于 control 唯一完成的 run（60 轮）。
4. **诚实声明：守卫未实际投递任何提醒**（advisory_delivered=0/3，
   pg_triggers=0）。both 臂与 control 的机制差异只剩：扩展注入的
   收尾申报协议（STATUS/REMAINING/EVIDENCE 要求）改变了 agent 的
   收尘认知。停滞消失是"知道要申报"带来的，还是方差——n=3 无法区分。
   这直接指向 Phase 2+ 的设计问题：**收敛提醒的触发阈值（>100 轮）
   在 900s 预算下从未到达**，需要按预算比例缩放阈值才能让提醒真正参战。

## 3. 对用户问题的回答（"守卫能否放大 AI 解决问题的能力"）

- **方向性证据：是**（33%→67%，停滞 2/3→0/3，轮次效率 12.8 倍）。
- **统计证据：否**（n=3，p=1.0）。
- **机制归因：未定**（投递为零，疑似申报协议效应；需更大 n 与
  阈值按预算缩放后的对照）。
- 落带任务的发现方法（硬题+时间预算）本身可复制：这是本轮的
  方法论产出。

## 4. 欠功效与下一步

- 需要 ≥30 run/臂才可能对 +34pts 达到 p<0.05（每 run 4-15 min）。
- 两个方向：a) 同任务扩 samples（免费窗口累计，断点续跑就绪）；
  b) 阈值缩放实验（stall 阈值 = f(预算)），让提醒在短预算下也能触发。
- 数据：runs_smoke.jsonl 全部 6 run 原样留存（eigen 共 6 行）。
